# `server/` — AQUADIVE backend skeleton (P8-2)

**Status: P8-2 skeleton, 2026-11-18. Accepted by the owner for local development only. Not production-ready. Not connected to the game. Play money only.** Security review: §11.

**P8-3c, 2026-11-19 (local development only; accepted for local development on 2026-11-23, committed locally, not pushed):** the package also compiles the shared fairness library and contains a node:crypto fairness adapter, a chain vault and a development-only in-memory chain store (`src/fairness.ts`, `src/fairness/`; §12). None of it is imported by the entrypoint, the HTTP routes or the WebSocket gateway: the running server behaves exactly as in P8-2.

**P8-4a, 2026-11-23 (offline development and testing only; accepted for local development only and committed locally, not pushed; M-3 build integrity open):** the engine bundle now exports only a sealed round runner, and `src/round/` precomputes immutable RoundScripts offline from isolated development chains (§14). Nothing in the entrypoint, the HTTP routes or the WebSocket gateway reaches it.

**P8-4a-1, 2026-11-23 / 24 (offline development only; accepted for local development only and committed locally, not pushed):** a reviewed, Git-tracked trusted manifest (`integrity/engine-manifest.json`) of the offline round runtime; the build fails and the loader refuses on any mismatch (§15). M-3 is addressed within the trusted-build model only; the in-process check verifies itself and is not a defence against deliberate tampering of the deployed build, same-process code or a rewritten manifest (§15 "Trust boundaries").

A Fastify service with health endpoints and a WebSocket endpoint that performs the protocol v1 (DRAFT) `hello` → `welcome` handshake and nothing else. There is no round engine, no authentication, no wallet, no ledger, no database and no money. The running game does not talk to it: the frontend stays in local demo mode.

The owner authorized P8-2 as a narrowly scoped Phase 8 implementation exception (2026-11-18) while Phase 7 stays open. Design: `docs/09_BACKEND_ARCHITECTURE.md` §29 P8-2, §8.3–§8.4, §9.1, §9.5, §23.2, §23.4; owner decisions A–D: docs/09 §37.

## 1. What it does, and what it does not

| Does                                                                                                             | Does not                                                       |
| ---------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `GET /health/live`, `GET /health/ready`                                                                          | Run rounds, ticks, crashes, bonuses or any game state          |
| WebSocket `GET /ws`: Origin check, connection limits, hello timeout, frame-size and frame-rate limits, heartbeat | Authenticate anyone (`auth.resume` is refused)                 |
| `hello` → `welcome` with the negotiated protocol, a fresh connection id, the server time and 60 Hz               | Send a round snapshot (none exists) or private player state    |
| Refuse every other request with an `error` frame before processing                                               | Place, cash out, pick, settle, pay or store anything           |
| Close connections with documented codes; graceful shutdown                                                       | `sync.request` handling, `pong`, broadcasts (later milestones) |

## 5. HTTP

| Route               | Answer                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `GET /health/live`  | `200 {"status":"live"}`                                                                   |
| `GET /health/ready` | `200 {"status":"ready"}`; `503 {"status":"draining"}` once shutdown began                 |
| anything else       | `404 {"error":"not-found"}`; other failures `{"error":"<kind>"}` with no message or stack |

Every response has `cache-control: no-store` and `x-content-type-options: nosniff`. Request bodies are limited to 1 KiB (no route takes one), requests time out after 10 s, keep-alive after 5 s. "Ready" means only "accepts new WebSocket connections": there is no database or round to be ready for yet.

## 6. WebSocket `/ws`

### 6.1 Upgrade admission (HTTP, before any WebSocket exists)

| Condition                                                                   | Answer |
| --------------------------------------------------------------------------- | ------ |
| Draining                                                                    | `503`  |
| `Origin` header missing, repeated, `null`, or not exactly an allowed origin | `403`  |
| Total or per-address connection limit reached                               | `503`  |

The Origin check stops cross-site use of the socket from browsers. Any non-browser client can send any Origin, so it is **not authentication**.

### 6.2 Frame pipeline

Socket options: `maxPayload` = 4 KiB (the protocol's client frame limit), permessage-deflate off. Then, for every inbound frame (`src/gateway/connection.ts`):

| Step                                                                                                                                                         | Failure → answer, close code                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| Size (by `ws`, from the frame header, before the body is buffered)                                                                                           | close `1009`                                                                                                      |
| Valid UTF-8 text, correctly masked frames (by `ws`)                                                                                                          | close `1007` / `1002`                                                                                             |
| Rate: token bucket, 30 / s, burst 60, **before decoding**                                                                                                    | `error rate-limited`, close `4008`                                                                                |
| Text frames only                                                                                                                                             | `error malformed`, close `1003`                                                                                   |
| `decodeClientFrame` (protocol library): size, UTF-8, nesting ≤ 6, JSON, `__proto__` / `constructor` / `prototype` keys, version, strict envelope and payload | `error <code>`: `protocol-unsupported` → `4001`; `frame-too-large` → `1009`; `malformed`, `unknown-type` → `1008` |
| Before the handshake, anything but `hello`                                                                                                                   | close `1008` ("hello required"), no frame                                                                         |
| `hello` with no common protocol major (`negotiateProtocol`)                                                                                                  | `error protocol-unsupported` (`re` = hello id), close `4001`                                                      |
| No `hello` within 5 s                                                                                                                                        | close `1008` ("hello timeout")                                                                                    |
| A second `hello`                                                                                                                                             | `error malformed`, close `1008`                                                                                   |
| Any other valid request after the handshake                                                                                                                  | refused, see 6.4; **the connection stays open**                                                                   |

A peer that does not answer a WebSocket ping within one heartbeat interval is disconnected. A closing socket that does not finish the close handshake within 2 s is destroyed. On shutdown every connection is closed with `1001`, and shutdown waits for them (bounded by the grace period).

### 6.3 The welcome

```jsonc
{
  "v": 1,
  "t": "welcome",
  "seq": 1,
  "ts": "<send time ms>",
  "re": "<hello id>",
  "p": {
    "protocol": 1,
    "sessionId": "<fresh UUID v4>",
    "serverTimeMs": "<build time ms>",
    "tickHz": 60,
  },
}
```

- `sessionId` identifies **this connection** only. No player, account or authenticated session exists.
- **No `snapshot`:** the server has no authoritative round to report (protocol amendment, `src/protocol/README.md` §20). Nothing is invented: no round id, number, commitment, phase or game state.
- **No `player`:** private state is never sent to an unauthenticated connection.
- A welcome without a snapshot authorizes no `bet.place`, `bet.cashout` or `bonus.pick`.

### 6.4 Refused requests

| Request                                  | Answer (`error`, `re` = the request id)                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| `bet.place`, `bet.cashout`, `bonus.pick` | `auth-required` (money commands need an authenticated session; none can exist) |
| `auth.resume`, `sync.request`, `ping`    | `server-busy` (not available on this server yet)                               |

Both codes are registered as **transient**: refused before processing, not stored, the same id may be resent. Nothing is looked up, stored or forwarded. The protocol registry has no dedicated "not available" code; adding one would be a further protocol change (an owner decision, see §10).

**These are temporary P8-2 skeleton responses, not permanent contract behavior.** They describe this skeleton only. Each request type gets its real behavior in its own milestone (identity P8-8, resync P8-5 / P8-6, `ping` / `pong` with the client network mode). A client must not treat `server-busy` here as real load, or `auth-required` as the server's lasting answer to a money command. No network client may be built against this skeleton (§11.3).

## 7. Logging

Fastify's built-in pino logger (no separate dependency), JSON lines to stdout. Redacted: `authorization`, `cookie`, `sec-websocket-protocol` headers, and `ticket`, `token`, `password` fields at the top level or one level down. Request URLs are logged as the path only (no query string). The gateway never logs frame contents; it logs connection ids, close codes and decode failure codes with their safe `detail` (a schema path and issue kind, never input values). The logs include pino's default `pid` and `hostname`.

## 8. Dependency resolution (owner condition, Decision B)

The server consumes the original `../src/protocol` source; nothing is copied. Its bare `zod` import must resolve to **this package's** `zod` 3.25.76, never to the root's `node_modules`, and only one `zod` instance may load:

| Stage                      | How `zod` imported by `../src/protocol/*.ts` resolves                                                                                                                                                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type-check (`tsc`)         | `tsconfig.json` `paths.zod` → `./node_modules/zod` for every file                                                                                                                                                                                               |
| Build                      | `tsc -p tsconfig.build.json` emits CommonJS for the server **and** the protocol into `dist/` (`dist/server/src/**`, `dist/src/protocol/**`). Node's lookup from `dist/src/protocol/` walks up to `server/node_modules` before any directory outside the package |
| Run (`npm start`)          | as built: every bare import resolves inside `server/`                                                                                                                                                                                                           |
| Dev (`npm run dev`, `tsx`) | `tsx` applies `tsconfig.json` `paths`, so the protocol source gets `server/node_modules/zod`                                                                                                                                                                    |
| Tests (Vitest)             | `vitest.config.ts` `resolve.alias` pins `zod` to `server/node_modules/zod`                                                                                                                                                                                      |

CommonJS output keeps the protocol's extensionless relative imports valid at run time without touching the shared source. Verified in a clean temporary copy holding only the root `package.json`, `src/protocol/` and `server/` with no `node_modules` anywhere (P8-2 report: `npm ci`, type-check, build, 135 tests, a runtime probe listing one `zod` package root inside `server/node_modules`, and the built entrypoint serving health and a handshake). `test/boundaries.test.ts` re-checks the single instance on every run.

`dist/` is Git-ignored (the root `.gitignore` `dist` rule). The root ESLint configuration lints `server/` unchanged; its root-level `dist` ignore does not cover `server/dist/`, whose built files are linted with no finding.

## 10. Limitations and open items

- Not production-ready: no TLS, no authentication, no metrics endpoint, no per-address connection-rate limit (docs/09 §9.5 "20 / min", only concurrent bounds here), no slow-consumer back-pressure, no load test (docs/09 §29's 5,000-connection target is not measured).
- Windows: `SIGTERM` cannot be delivered to a Node process, so graceful shutdown is tested in process (`createShutdown`); the `SIGINT` / `SIGTERM` handlers in `main.ts` are not exercised by the tests.
- Owner decisions: a dedicated "not available" error code instead of `server-busy` for `auth.resume` / `sync.request` / `ping`; the import rules of docs/09 §6.3 are enforced by a test, not a lint rule (the root ESLint configuration stays unchanged).
- Not done: physical-device testing, production load testing, any deployment.

## 11. Security review (P8-2 final acceptance, 2026-11-18)

Scope: the server as committed, for **local development only**. This review does **not** claim zero vulnerabilities or production security readiness. `npm audit` (2026-11-18): 6 high findings, of which **1 in production dependencies** (zod) and 5 dev-only packages that all trace back to one picomatch advisory.

### 11.1 zod 3.25.76: GHSA-mrhx-c7xc-m3w5 (high, CVSS 4.0 8.2, availability only)

Memory and time grow with the number of failing elements; a large enough array can exhaust memory. | Affected dependency        | `zod` 3.25.76, a direct production dependency (the protocol's validator). | Exploit preconditions here | An unauthenticated client would need a client→server schema that contains an array, and a frame large enough to hold many elements                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

### 11.2 picomatch 4.0.7: GHSA-fc5q-39xc-vjpf (high, ReDoS, dev only)

ReDoS through repeated single-branch extglobs, range `<= 4.0.7`; 4.0.7 is the latest release, so no patched version exists. It is installed only through dev tooling (Vitest 4.1.12, Vite 8.3.8, tinyglobby, fdir), never in the built server or its runtime dependencies (`npm audit --omit=dev` reports only zod). It evaluates only glob patterns from this package's own configuration, never network input. npm's suggested "fix" (Vitest 3.1.4) is a downgrade outside the approved 4.1.x and is not applied. Remaining risk: a hostile glob in project configuration, which is equivalent to code access. Review again when picomatch publishes a fix or when Vitest changes.

### 11.3 Refusal semantics (§6.4)

Verified on the built server against the protocol's own client decoder and `classifyRequestResponse`: each of the six refused request types returns exactly one `error` frame, with `re` = the request id, the next `seq`, payload `{ code, retryable: true }` only, and outcome **transient**. The connection stays open. Only `welcome` and `error` frames are ever sent. The refusal path is a static table lookup: no lookup, storage, forwarding, round, wallet, ledger or identity logic runs. The registry contract (`src/protocol/README.md` §9.1) makes these answers conservative: "this delivery was refused before processing; keep the request unsettled; resend only the same id". A client therefore never treats a refused bet as accepted or as finally rejected.

Limitations: `server-busy` is semantically imprecise (nothing is busy; the service does not exist yet). A well-behaved client following the contract will back off and retry indefinitely. This is harmless to the server (rate limit, connection bounds), but it is why **no network client may be built against this skeleton**. Before P8-6 each request type needs its real behavior, or the owner authorizes a dedicated code.

## 12. Fairness infrastructure (P8-3c, local development only)

**Status: delivered 2026-11-19; accepted for local development on 2026-11-23 (not production fairness certification); committed locally, not pushed. Not connected to the running server, the gateway or the game. Not production fairness. fv = 1 internal and experimental.** **P8-3c-3 security patch (indeterminate reveal ordering, compromised-chain cache invalidation): delivered and accepted for local development on 2026-11-23 (not production security certification); committed locally, not pushed.** Owner decisions: `docs/09_BACKEND_ARCHITECTURE.md` §40. ### 12.1 Build integration (P8-3c-0)

`tsconfig.json` adds `allowImportingTsExtensions` and `rewriteRelativeImportExtensions` (owner-approved), so `tsc` compiles the shared fairness source unchanged: its explicit relative `.ts` imports are emitted as `./x.js` into `dist/src/fairness/`. `src/fairness.ts` is the only bridge: it re-exports a named list from `../../src/fairness/index.ts` (the public barrel), never a private module, never through `@/`. Neither option changes the output of extensionless imports: the 31 P8-2 output files are byte-identical; 20 files are added. `test/fairness/build.test.ts` builds the server into a temporary directory and checks the emitted specifiers, the single compiled copy, the unchanged `main.ts` closure, and that the compiled code loads no `.ts` file and reproduces the full development dump. `npm start` is unchanged and loads no fairness module.

### 12.2 node:crypto adapter (P8-3c-1)

`src/fairness/crypto-node.ts` implements the library's injected `FairnessHashProvider` (SHA-256; HMAC-SHA256 with the key prepared once per round as a `KeyObject`) and `SecureRandomSource` (`randomBytes`). `createNodeFairnessCrypto()` returns it only after `assertFairnessCryptoReady`: the published SHA-256 / HMAC-SHA256 known answers, the fv = 1 development vectors end to end (chain link, round seed, three derived blocks), the HMAC key-copy contract (the provider must not keep the caller's key buffer) and random-source sanity (type, length, not all zero, two draws differ). Failures throw `crypto-provider-failed` or `secure-random-failed`; there is no fallback and no `Math.random`. Every Node `Buffer` is copied into a plain `Uint8Array` and zeroed; the `KeyObject` exists only in the prepared closure.

### 12.3 Chain vault and development store (P8-3c-2)

| Module                  | Responsibility                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `errors.ts`             | `ChainError` with a closed code set; messages carry no secret                                                             |
| `checkpoints.ts`        | Checkpoint geometry: x_N and every multiple of the interval (default 1,024, provisional)                                  |
| `chain-store.ts`        | The `ChainStore` interface, chain states and transitions, dispositions, stated guarantees                                 |
| `memory-chain-store.ts` | **Development-only** in-memory store: refuses production; volatile, single-process, not transactional                     |
| `chain-vault.ts`        | The only owner of chain secrets: new-chain workflow, reservation, round keys, classification, verified reveal, precompute |
| `round-keys.ts`         | `RoundKeys`: the one `RoundDerivation` of a reserved index; disposal; public-only serialization                           |
| `reveal.ts`             | Verification of a revealed seed against the revealed chain, in yielding slices                                            |
| `records.ts`            | Allow-listed public records (commitment, status, reservation, disposition, reveal)                                        |
| `audit.ts`              | Allow-listed audit events; `MemoryAuditSink` (neither durable nor tamper-evident)                                         |

**Round lifecycle.** `createChain({ length })` draws a fresh secure seed and stores the checkpoints → `reserveRound(chainId, requestId)` → `prepareRound(chainId, index, salt)` returns `RoundKeys` (the caller disposes them) → `classifyRound(chainId, index, disposition, reasonCode)` → `revealRound(chainId, index)`. `precompute(chainId, from, count)` caches upcoming seeds ahead of time.

**Rules.**

- Reservation is monotonic and keyed by a request id: a retry returns the same index; an index is never released or reused.
- The public salt is bound to the index before derivation and never changes (`salt-conflict`): a failed preparation cannot be retried with another salt.
- A derivation is issued once per index (`derivation-already-issued`).
- Dispositions `completed` (needs an issued derivation), `aborted`, `voided` and `indeterminate` are evidence only, with reason codes and history; `indeterminate` may be resolved once, by an explicit final classification; final values never change. No settlement or payout rule exists here, and nothing resolves an indeterminate round automatically.
- A reveal needs the round finally classified (`completed`, `aborted` or `voided`) and every earlier reserved index finally classified or revealed, because revealing x_j discloses all earlier seeds (`reveal-order-violation`). **`indeterminate` is not a conclusion (P8-3c-3):** an indeterminate round cannot be revealed (`round-not-concluded`) and blocks every later reveal exactly like an unclassified one until it is resolved. Unreserved (future) indices cannot be revealed. A repeated reveal returns the same record; a reveal that fails verification or contradicts recorded data moves the chain to `compromised`.
- The store compares and records but never hashes; the vault verifies every link before it records a reveal.

**Chain states.**

| State                                            | Reserve | Derive | Reveal / read secrets | Explicit transitions to               |
| ------------------------------------------------ | ------- | ------ | --------------------- | ------------------------------------- |
| `active`                                         | yes     | yes    | yes                   | `suspended`, `retired`, `compromised` |
| `suspended`                                      | no      | no     | yes                   | `active`, `retired`, `compromised`    |
| `exhausted` (automatic, at the last reservation) | no      | yes    | yes                   | `retired`, `compromised`              |
| `retired`                                        | no      | no     | yes                   | `compromised`                         |
| `compromised`                                    | no      | no     | no                    | none                                  |

Classification is recorded in every state.

**Failures and restart.** Nothing is rolled back into a reusable state. A failure before a reservation reserves nothing. A failure after it (an ambiguous result) is retried with the same request id and receives the same index. A failure while preparing round secrets returns no keys; the salt stays bound and a same-salt retry succeeds. If an issued derivation cannot be delivered, its keys are disposed and the index must be classified. A failure during a reveal records nothing; the retry succeeds or replays. **After a process restart every earlier chain is `unknown-chain`**: the in-memory store cannot recover, does not pretend to, and a new chain needs the explicit `createChain` workflow. Durable recovery, cross-process uniqueness and encrypted checkpoints are P8-7 (recorded as `it.todo` contract requirements in `test/fairness/memory-chain-store.test.ts`).

**Production refusal.** `new MemoryChainStore({ mode })` requires `mode` `development` or `test` and refuses unless `NODE_ENV` is unset, `development` or `test`. Its `guarantees` state `durable`, `crossProcessIndexUniqueness`, `multiStepTransactions` and `productionUse` as `false`.

### 12.4 Secret handling (defense in depth)

**Cached seeds (P8-3c-3).** The precompute cache is an optimization, never an authority. The vault disposes a chain's cached seeds as soon as it observes that the chain may no longer derive: on its own transitions, on every chain snapshot it reads, and on every store refusal or integrity error for that chain (`invalid-chain-state`, `reveal-conflict`, `reveal-verification-failed`, `unknown-chain`, `store-closed`), synchronously, before it audits or yields. A store-detected `reveal-conflict` is additionally audited as a `compromised` transition. `precompute` stages seeds privately and installs them only if, after its last yield, the vault is not disposed, the chain may still derive and the chain's cache epoch (advanced by every drop) has not moved; otherwise it disposes them and fails closed. `prepareRound` likewise refuses (`invalid-chain-state`, same-salt retry allowed) if the cache was dropped while it reconstructed a seed. **Limitation:** a vault learns of an out-of-band compromise (another vault, an operator) only on its next interaction with that chain; until then its cached seeds stay in memory.

Chain seeds, checkpoints and unrevealed round seeds exist only as `SecretBytes` or short-lived buffers that are zeroed after use. The vault, the store and `RoundKeys` serialize and inspect as redacted markers; records and audit events have fixed allow-listed fields with no free text; errors carry codes and public indices only. Tests render every object the vault produces (JSON, `String`, template literals, `util.inspect` with hidden fields, keys, error messages and stacks) and find no chain link before its reveal, and only the revealed links after it. Disposed secrets, disposed round keys, a disposed vault and a closed store refuse every later use. **Not protected:** memory inspection, heap snapshots, debuggers, the OpenSSL key behind a `KeyObject` (released by the garbage collector), engine-internal copies and deliberate extraction. Erasure is best effort.

### 12.5 Event loop and performance

Every hash walk (chain creation, precompute, seed reconstruction from a checkpoint, long reveal verification) runs in slices of at most 256 links and yields between slices. With precomputed seeds, preparing and revealing a round needs no hashing beyond the reveal's one-link check (p99 ≈ 0.2 – 0.3 ms measured). Measurements on battery with other load are **informational only; D7 stays NOT VERIFIED** (docs/15). The slice size (measured p99 ≈ 2.04 – 2.10 ms against the provisional 2 ms target) and the checkpoint interval are open tuning decisions. No scheduler, worker pool or background job exists.

### 12.6 Zod S-1: limited gate exception (owner, 2026-11-19)

§11.1 made the zod review a mandatory gate "before P8-3 or any later milestone starts". The owner granted a **narrow exception for this offline, development-only fairness infrastructure only**, conditional on: no new WebSocket handler, no new HTTP endpoint, no frontend network client, no untrusted protocol message decoding, no zod schema change, no expansion of production network exposure, and no connection to the live server lifecycle. P8-3c meets every condition: the fairness modules import neither zod nor the protocol (a source-rule test), the startup / HTTP / gateway import closure never reaches them (a boundary test), and the built entrypoint loads no fairness module (a run-time probe). No dependency changed. **S-1 is not resolved.** It remains mandatory before a new browser network client, before expanding the affected untrusted decoding paths, and before production readiness.

### 12.7 Limitations and open items

- Development only: no durable store, no encryption at rest, no KMS, no PostgreSQL or Redis, no tamper-evident audit, no cross-process index uniqueness (P8-7).
- No round orchestration, no `SeededRoundAuthority` binding, no `GameEngine` on the server, no endpoint, message handler, public commitment or verifier (P8-4 and later).
- Open: public salt source, fv = 1 freeze, Node 22 verification, controlled performance validation (D7), slice size and checkpoint interval, selective-voiding operations, Zod S-1.
- P8-3c-3: an indeterminate round that is never resolved blocks every later reveal of its chain indefinitely (fail closed by design). Who may resolve it, when, and on what evidence is an owner / operations decision (selective voiding, D10), not encoded here. A vault does not learn of an out-of-band compromise before its next interaction with that chain.

## 14. Offline RoundScript precomputation (P8-4a, offline development only)

**Status: delivered 2026-11-23 under owner decisions K1 – K12 (docs/09 §42); acceptance corrections M-1, M-2, M-2b, L-1, L-2 and the M-3 documentation applied 2026-11-23; ACCEPTED FOR LOCAL DEVELOPMENT ONLY (2026-11-23) and committed locally, not pushed. **The runner (K1, K4, K5).** One fresh `GameEngine` per round, built only from `SeededRound.bind(derivation).deps`. Fixed ticks: `advance(1/60)` must move `engine.tickCount` by exactly one, and the runner's own counter must equal it. Betting is exactly 300 ticks (entry diving at tick 300, where the crash point is drawn). It stops on the tick whose resulting state is `crashed` (crash) or `bonus` (floor: impact + 84 ticks, where the chests are rolled), so a second round's crash point is never drawn. It records, for every tick whose resulting state is `diving` (index i = tick 300 + i), the multiplier, boost and worldY; every creature with its attributes, spawn tick and consumption tick; outcome, crash point, jackpot, chests, final world and draw counts. It fails closed (`RoundRunnerError`, fixed code, no cause) on any other event or state sequence, a tick mismatch, more than 2,500 ticks, a snapshot that disagrees with the observations, or a draw count outside the unchanged outcome functions' fixed rules (crash 2, or 1 exactly for a 1.00× crash point; jackpot 2 and chests 6 for a floor round, 0 otherwise; world = 7 × creatures). The engine, its mathematics, its draw order and the stream separation are unchanged; all 16 replay pins reproduce.

**Validation and the RoundScript (K5, K6, K11, K12).** The server never trusts the bundle's result: it re-encodes it canonically (refusing getters, prototypes, −0, NaN, Infinity) into a detached copy and checks every field — exact key sets; the tick accounting; the analytic bound (a dive of at most 1,290 ticks — the boost-free floor dive — and a terminal tick of at most 1,674); value ranges of every outcome function; monotonic depth; samples below the crash point; creature ids, kinds, ranges and lifecycle; final world consistency; the draw-count rules. A `RoundScript` has public metadata (`scriptVersion`, `status: "experimental-internal-offline"`, profile and version, fv, chain id, chain index, salt) and secret content (everything else), readable only through `secretContent()`, `secretDigest()` and `secretCanonicalBytes()` (a fresh copy). `JSON.stringify`, `String`, templates and `util.inspect` show the public part and `[redacted secret]`. It holds no seed, key, stream, derivation, RoundKeys or engine. Canonical bytes: sorted keys, ECMAScript shortest round-trip numbers, ASCII strings without escapes; digest = SHA-256(`"AQUADIVE-ROUNDSCRIPT\0v1\0"` ‖ bytes), INTERNAL (K11).

**The loader.** `loadEngineRuntime(crypto)` takes no path: the bundle is `<build>/engine/engine.cjs`, resolved from the loader's own compiled location `<build>/server/src/round/`. It refuses (`RoundScriptError`): an unloadable or unparsable bundle (`runtime-unavailable`); any other export surface or profile (`runtime-incompatible`); a bundle whose fairness dependency, or any loaded module exporting `RoundDerivation` / `SecretBytes`, is not the bridge's instance — another path, or on Windows another drive-letter case (`runtime-duplicate-fairness`); a failed known answer (`runtime-known-answer-failed`). Only the server's compiled build can run it: under Vitest the server's source and the compiled bundle would be two fairness instances, so the tests run the compiled build in fresh processes.

**The known answers are a regression check, NOT bundle authentication (acceptance finding M-3; unresolved).** The three known answers (A1, B1, A7) catch accidental breakage, but their coverage is incomplete: crash points up to 28.9× only; no 1.00× round, no crash above 100×, no round at the 200× multiplier clamp, no jackpot above 200, no goldfish-consumption path. There is no hash or signature check of `engine.cjs`. **Demonstrated in the acceptance audit:** a bundle whose multiplier clamp `Math.min(m, 200)` was edited to `Math.min(m, 30)` (which changes RTP) loaded with `load: ok`; over 3,000 rounds no crash exceeded 30× (88 do with the real bundle). Anyone who can write the build output can change gameplay mathematics without the loader noticing. **Mandatory security gate, still open: build-integrity verification must exist before the engine is connected to any live round scheduler (P8-4b or later).** Proposal, not implemented: (1) a build-time SHA-256 manifest of `engine.cjs` and the compiled fairness and round modules, produced by the build and checked by the loader against a trusted reference that the build output cannot overwrite (for example a value committed in reviewed source or provisioned by the operator); (2) broader, independently selected known-answer scenarios — a crash above 100×, a 1.00× round, the 200× clamp, each jackpot tier, goldfish consumption — whose expected values come from the spec-only generator, not from this engine. The A1 / B1 digest candidates come from the same engine source and are not independent truth.

**Isolation and the offline disposition (K8).** `createOfflineRoundEnvironment({ mode: "development" | "test" })` creates its own private `MemoryChainStore` (which also refuses a production `NODE_ENV`), vault and audit sink; no outside store or vault can be passed, so no exercise can consume an index of a chain meant for live play. Chains: `createChain` (fresh random development chain) or, in test mode only, `importPublicTestVectorChain` (the public fv = 1 development vectors). Disposition, offline only and **not** the production selective-voiding policy (D10 / OD-11 open): a built script → `completed` / `offline-script-built`; any failure after the reservation → `aborted` / `offline-script-failed`; never `voided` or `indeterminate`. If the classification itself fails the index stays open (it then blocks later reveals: fail closed) and the call throws `disposition-failed`. A request id is used at most once per environment; a replay is refused before the vault is asked.

**Private vault (acceptance correction M-2).** The `ChainVault`, its store and its audit authority are private fields of the environment; nothing returns them. Before the correction a public `env.vault` let a caller reserve and prepare a round, inspect its outcome and then classify it `completed` or `voided` at will (selective voiding). The environment now exposes only: `createChain`, `importPublicTestVectorChain` (test mode), `prepareScript`, `verifyScript`, `chainStatus` (read-only status record), `revealRound` (the vault's concluded-only, in-order reveal, and only for an index this environment prepared and already classified), `restrictChainForTest` (test mode only: one way to `suspended` or `compromised`, fixed reason code `offline-test-restriction`; it changes no round's disposition and a chain can never return to `active`) and `close`. No `classifyRound`, `prepareRound`, `reserveRound` or general `transitionChain` is reachable, so no caller can choose `completed`, `voided`, `aborted` or `indeterminate` after seeing an outcome. This keeps the offline policy above; it is not a production D10 / OD-11 policy. Delegate failures are `chain-unavailable` with the vault's fixed reason code.

**Run-time construction guard (acceptance correction M-2b).** TypeScript's `private` is not a run-time boundary: before the correction, `new OfflineRoundEnvironment("development", crypto, wrapper, sink)` from JavaScript skipped the runtime check, and a wrapper that called the real runtime and threw on unwanted outcomes had them classified `aborted` (selective abort). The JavaScript constructor now requires a module-private construction capability that only `createOfflineRoundEnvironment` / `create` pass, and itself re-checks the mode (`development-only: unsupported-mode`), the crypto provider (`unverified-runtime: unverified-crypto`) and that the runtime is the very object `loadEngineRuntime` verified (`unverified-runtime: unverified-engine-runtime`). Direct construction, `Reflect.construct`, a subclass or `instance.constructor` is refused with `invalid-request: construction-refused` before any store exists; a wrapper, forged runner, copy, prototype child, proxy or bound delegate of a real runtime is refused even though it delegates to it. The loader also binds the bundle's `runSeededRound` and `RoundRunnerError` once, before its known answers: the bundle's exports object is writable, and a per-round lookup let in-process code that replaced the export after verification reproduce the selective abort through a legitimate environment.

**Failure handling.** On every path the RoundKeys and with them the derivation, its streams and the seeded round are disposed; no partial result is returned; every outcome is audited (`script-built`, code null; `script-failed`, one of the fixed `RoundScriptError` codes; K7). Errors name a fixed code and at most one fixed reason code of the failing layer (`chain-unavailable: invalid-chain-state`, `runner-failed: tick-mismatch`, …).

**Verification after a reveal (acceptance corrections M-1, L-1).** `await env.verifyScript(script, revealRecord)` (asynchronous since the correction) trusts only the environment's own records, never the caller's. It reads, without changing anything, the script's chain and index from the private store and refuses (`reveal-mismatch`, identical for every case) unless: the chain exists in this environment and is not `compromised`; the index is finally classified and **already revealed through the vault** (`revealRound`, whose verified reveal the store records); and every field of the caller's record (kind, status, fv, chain id, chain length, index, seed, previous link, salt, disposition) equals the authoritative record. Before the correction it trusted the caller's record: a random chain the environment never had, with internally consistent hashes, verified `match: true`, and so did a false `chainLength: 999`. It then re-checks the authoritative seed against the authoritative commitment (previous link, `SHA-256^j(x_j) = x_0`, j hashes), recomputes the round from the authoritative seed and salt, and compares canonical bytes; on a mismatch it lists the altered field paths (names only; after the reveal the content is public). Verification never reveals, records, classifies, transitions or creates anything, so it cannot publish a seed or move the reveal frontier; an exact, correct record of a concluded but unrevealed round is refused. Every fallible construction (the seed copy, `RoundKeys`) is inside the guarded scope; the temporary `SecretBytes` copy and the `RoundKeys` are disposed in `finally`; construction failures (for example a malformed salt, which before the correction escaped as a raw `FairnessError("invalid-salt")`) map to `reveal-mismatch` with no cause. The loader's known-answer derivations dispose their temporary seed copy the same way. `parseRoundScript(hash, bytes, expectedDigest)` refuses any alteration of stored bytes without detail.

**Limitations and residual risks.**

- Offline only: synchronous whole-round precomputation must not run on a live loop, an HTTP / WebSocket handler or at startup (K10). D7 is **NOT VERIFIED**; the numbers in docs/15 are provisional (battery power).
- The digest candidates are **not owner-approved** (K9); the outcome kind of A1 / B1 / A7 comes from the P8-3b reference runner, not from the independent generator.
- **The bundle is not authenticated (M-3, open security gate):** a targeted edit of the multiplier clamp (200× → 30×) passes the loader. Build-integrity verification is mandatory before any live scheduler connection (see "The known answers are a regression check" above). _P8-4a-1 (§15): addressed within the trusted-build model — the trusted manifest now refuses this bundle; the remaining limits are listed in §15 "Trust boundaries"._
- `RoundKeys.create` stays a public static and `RoundDerivation.block()` stays public (P8-3c design); the environment never returns either, but in-process code can still call them.
- In-process code is trusted: code in the same Node process that rewrites shared built-ins (for example `WeakSet.prototype.has`, used by the crypto and runtime registries) or the fairness classes can defeat any in-process check, the construction guard included. Only process isolation would change that.

- Inside the bundle, reflection still reaches `SeededRoundAuthority` from a round, and `GameEngine` still accepts any duck-typed authority (§13); since K2 no round leaves the bundle, so this is reachable only by code that is bundled.
- Verification after a reveal hashes j times (offline); it is not a public verifier.
- Erasure stays best effort (JavaScript); memory inspection is out of scope.

## 15. Build integrity of the offline round runtime (P8-4a-1, offline development only)

**Status: delivered 2026-11-23 under owner decisions I1 – I9 (docs/09 §43); ACCEPTED FOR LOCAL DEVELOPMENT ONLY (2026-11-24, final acceptance review) and committed locally as one isolated commit `feat(server): add build integrity verification (P8-4a-1)` on top of `011facc`, not pushed. M-3 is addressed within the trusted-build model: an unreviewed change of the protected output fails the build, and the loader refuses an altered engine bundle before any of its code runs. It is NOT a complete defence: the loader's own modules verify themselves (see "Trust boundaries"), and it does not make the in-process runtime tamper-proof.**

**Trusted manifest (I1, I2).** `integrity/engine-manifest.json` — reviewed, Git-tracked, **outside** the generated build (`dist/`) — lists the 29 files of the offline round runtime's actual module closure in the build, each with its size and SHA-256: the engine bundle `engine/engine.cjs`; the loader and pipeline `server/src/round/*.js` (8); the server fairness modules `server/src/fairness/*.js` (10) and the bridge `server/src/fairness.js`; the compiled shared fairness library `src/fairness/*.js` (9). The list is the measured closure: a fresh process that loads `prepare.js` and runs `loadEngineRuntime` loads exactly these 29 build files and nothing else from the build (a compiled-runtime test checks it). Frontend artifacts, `src/protocol`, the HTTP routes and the gateway are not in it.

Schema v1 (canonical text only — `JSON.stringify(manifest, null, 2)` plus one LF):

```json
{
  "schema": "aquadive.engine-integrity",
  "schemaVersion": 1,
  "algorithm": "sha256",
  "files": [{ "path": "engine/engine.cjs", "bytes": 38938, "sha256": "2d1e5bf8…" }]
}
```

Keys in exactly that order; `files` sorted by path, unique; every path must match one fixed pattern (relative POSIX paths in the four protected directories or the bridge; no `..`, absolute path, backslash, subdirectory or other extension); positive sizes; lowercase 64-hex digests. A duplicate key, reordering, CRLF, an extra field or a missing required file (bundle, loader, `integrity.js`, `prepare.js`, bridge, fairness index) is refused.

**Verification.** `src/round/integrity.ts`, called by `loadEngineRuntime`:

1. **Before the bundle loads:** read the trusted manifest from its fixed location (`<build>/../integrity/engine-manifest.json`; a regular file reached without a link), check every protected directory (a plain directory at its own real path, regular files with protected names only, nothing extra) and every listed file (regular, not linked or redirected, same size, same SHA-256 — hashed with the verified fairness hash provider).
2. **After loading:** every module in the module cache that lies in a protected location must be the manifest's file at exactly its path; a protected file loaded twice under another spelling (on Windows another case or drive-letter case) is refused — other Windows spellings of the same file (8.3 short names, `\\?\` or UNC paths) are not recognized as duplicates (see "Trust boundaries"); every module the bundle and the loader required, transitively, must be a manifest file (a bundle that requires anything else is refused).
3. **After the known answers:** the files are hashed again and the module cache is checked again.

Every refusal is `RoundScriptError("runtime-integrity-failed", <reason>)` (I8) with one fixed reason — `manifest-missing`, `manifest-not-regular`, `manifest-malformed`, `manifest-not-canonical`, `manifest-incomplete`, `protected-directory-invalid`, `file-missing`, `file-not-regular`, `file-path-mismatch`, `unexpected-file`, `size-mismatch`, `digest-mismatch`, `unexpected-module`, `duplicate-module-instance` — and never a path, size or digest. The code is in the audit's `script-failed` allow-list.

**Build and update workflow (I1, I4).** `npm run build` ends with `node scripts/engine-integrity.mjs verify`: it recomputes the build's manifest with `node:crypto` (it runs none of the build's code) and requires its canonical text to equal the trusted file byte for byte. On a mismatch it prints only the affected paths (`changed:` / `missing:` / `unexpected:`), removes `dist/engine/engine.cjs`, and exits 1. Nothing in the build writes the trusted manifest. `node scripts/engine-integrity.mjs candidate` prints a candidate to stdout and writes nothing. A legitimate change of protected output therefore needs a deliberate, separately owner-approved update: build a clean checkout, run `candidate`, review the difference to the tracked file, and only after the owner's approval replace `integrity/engine-manifest.json` in its own reviewed change. **Never regenerate it to make a failing build or test pass.** Comment-, whitespace- and line-ending-only engine source changes do not change the protected output (verified by real builds), so they need no update; a fairness source comment does change compiled output (tsc keeps comments) and is refused until the manifest is updated.

**Known answers (I6) — regression, not authentication.** The loader runs nine known answers: the three P8-4a development rounds and six rounds of a new public known-answer chain (`KNOWN_ANSWER_CHAIN_V1`: 2,048 links from a fixed phrase, salts A, B and C) — the 200× clamp, a crash point above 100×, exactly 1×, the 1.01 floor, a tier-3 jackpot floor, and a round that consumes three goldfish. Each is compared value by value and by the **independent record digest of the whole round** (every tick sample, creature, spawn and consumption tick, the final world and the draw counts). The tests compare all 45 independent vectors (16 development rounds and 29 known-answer rounds that cover, for every salt, exact 1×, the 1.01 floor, above 100×, the 200× clamp, a crash during a goldfish boost, all three jackpot tiers, a rare chest, one and two goldfish consumptions). They were selected by a fixed rule — the **first** index per salt and category — and a test proves that no earlier index qualifies. A bundle that is edited to reproduce these rounds would pass them; the trusted manifest is what refuses an altered bundle.

**Independent reference (I5).** `test/independent/` (TEST ONLY; never bundled; imports nothing from `src/` or `server/src/`): `spec-impl.mjs` (the reviewed P8-3a spec-only draw implementation, copied verbatim from the Git-ignored QA area, body blob `4af5b751…`; excluded from Prettier to stay verbatim), `reference-round.mjs` (outcome formulas, world draw order and the diving tick pipeline transcribed from the engine source; it reproduces the production runner's complete output for every round tried — 316 in QA and the 45 vectors in the tests), `generate-vectors.mjs` and its output `vectors-v1.json` (a test regenerates it and compares the data). It is a second, separately written implementation of the same rules: it detects changes of the engine's mathematics, draw order or tick pipeline; it does not prove the rules themselves correct.

**Line endings and reproducibility (I7).** `.gitattributes` keeps the protected sources, build inputs, the trusted manifest and the independent generator LF in every checkout. Evidence on this machine (Windows, Node 24.21.0): the 59-file build is byte-identical from the working tree (26 protected sources CRLF in it) and from a pure-LF `git archive` copy in another directory; real builds of copies with every protected source converted to CRLF, or with comment- or whitespace-only engine edits, verify against the trusted manifest; the 200× → 30× source edit does not. **Linux and Node 22 were not available (no WSL distribution, no Docker, only Node 24.21.0): cross-platform reproducibility and Node 22 compatibility remain unverified (I9 OPEN).**

**Trust boundaries — what this does NOT protect against.**

- **Time of check / time of use.** The files are hashed, then loaded by Node's module loader, which reads them again; a privileged process that swaps a file between the hash and the load, or that restores it afterwards, is not detected. The second hash narrows the window; it does not make check and use atomic. Modules required before `loadEngineRuntime` runs (the fairness library, the round modules, `integrity.ts` itself) are already executing when they are hashed. Loading from the hashed bytes would need a custom module loader (not authorized).
- **The checker verifies itself.** The runtime check is run by protected modules that are already loaded: `engine-runtime.js`, `integrity.js`, the fairness hash provider and, through `prepare.js`, every other protected server and fairness module (28 of the 29 files). Only the engine bundle is verified before any of its code runs. A post-build edit of those modules is detected at load time only while the edit leaves the check itself intact (an accidental or unrelated change); a deliberate edit can disable it — the final acceptance review showed a build with `verifyBuildIntegrity` emptied and a bundle altered for one rare round index loading without error against the unchanged trusted manifest. `node scripts/engine-integrity.mjs verify` (a separate process that runs none of the build's code) refused that build. Against deliberate tampering of the deployed build, rely on that out-of-process verification, a read-only deployment image and trusted CI, not on the in-process check.
- **Windows path spellings.** A protected module loaded a second time under a different drive-letter case is refused, but other spellings of the same file — 8.3 short names, `\\?\` long-path prefixes, UNC administrative shares — are not recognized as the same file (shown in the final acceptance review for a round module). Loading under such a spelling needs code in the same process; a second fairness instance is still refused by class identity.
- **Both build and manifest.** An attacker who can rewrite the build AND the trusted manifest defeats it (the tests show what the remaining defence-in-depth layers still catch, for example the 30× clamp through the expanded known answers; a change limited to rounds the known answers do not play passes them).
- **Same-process code.** Code running in the same Node process can change loaded modules or JavaScript built-ins (for example the `WeakSet`, `fs` or `crypto` functions the checks use); no in-process check can defend against it.
- **Build machine, dependencies and deployment.** A compromised build machine, toolchain (TypeScript, rolldown, Node, `node:crypto`) or deployment environment can subvert the build and the verification itself. The manifest does catch an unreviewed dependency or toolchain change that alters the protected output, because the build then fails. A read-only deployment image, trusted CI that builds from reviewed commits and checks the manifest, and running the engine in a separate process are independent controls, not provided here.

**Tests.** `test/round/integrity.test.ts` (schema, canonical form, 25 malformed manifests, protected-set rules on fake builds, agreement of the build tool with `integrity.ts`, no write path to the trusted manifest); `test/round/round-runtime.test.ts` "build integrity" (the clean build matches; one-byte bundle change, the 200× → 30× clamp at two sizes, changed compiled shared and server fairness code, changed round-preparation code and known answers, missing bundle, server fairness and preparation modules, an extra round module, a second bundle, a nested directory, a protected directory replaced by a junction, a missing / malformed / CRLF / duplicate-key / extra-field / path-traversal / incomplete / stale manifest, a manifest reached through a junction, a mismatch while every known answer passes, the 30× bundle with a rehashed manifest, a bundle that requires an unprotected module, a round module loaded under another drive-letter case, the build tool's verify and cleanup, error sanitization) and "independent known-answer vectors"; `test/round/integrity-build.test.ts` (real builds of source copies: unchanged, all CRLF, comment and whitespace only, the clamp edit, a fairness comment).

## 16. Offline preparation worker (P8-4b-0, offline development only)

**Status: delivered 2026-11-24 under the owner's P8-4b-0 decisions; final hardening and acceptance review 2026-11-24 (owner-approved protected-set expansion, below). ACCEPTED FOR OFFLINE LOCAL DEVELOPMENT ONLY (owner, 2026-11-24, with conditions) after an independent final re-verification (docs/15); committed locally, not pushed. OFFLINE DEVELOPMENT AND TESTING ONLY — no scheduler, no network integration, no cashout, no settlement, no production voiding policy (D10 / OD-11 and C4 / OD-8 stay open). PLAY MONEY ONLY.** Nothing in the application startup, the HTTP routes or the WebSocket gateway reaches it (boundary and run-time tests).

**Components (`src/prep/`).**

- `prep-worker.ts` — the `worker_threads` entry, started only from its fixed compiled location. It creates its own `OfflineRoundEnvironment` (P8-4a), so the engine runtime is loaded and verified **in the worker** (trusted manifest, export surface, profile, one fairness instance, known answers), and the environment's vault, `MemoryChainStore` and audit sink live and die there. It creates its own chain (a fresh random development chain, or in test mode the public fv = 1 vector chain) and prepares requests strictly one at a time; the vault assigns every index.
- `protocol.ts` — the message contract and its validators (exact keys, plain data, fixed codes, in both directions). Main → worker: `prepare { requestId, saltHex }`, `shutdown`. Worker → main: `ready`, `prepared { requestId, chainIndex, digest, bytes }`, `failed { requestId, code, reason, indexState, chainIndex }`, `rejected`, `fatal`, `closed`.
- `controller.ts` — `PrepWorkerController.start({ mode, chain, chainLength?, maxInFlight? })`: no path, entry, code, module or runtime is accepted; production `NODE_ENV` is refused; the build is verified against the trusted manifest on the main thread too; one worker is started with `eval: false` and no inherited `execArgv`; only `start` can construct a controller. `prepare(requestId, saltHex)` refuses a malformed id or salt, a reused id and anything beyond `maxInFlight` (at most 2, the look-ahead bound) **before sending**, so none of them reserves an index. Each result is re-parsed and fully re-validated with `parseRoundScript` and the reported digest, and must belong to the worker's chain with exactly the next index.

**What crosses the thread boundary.** Main → worker: only `prepare { requestId, saltHex }` and `shutdown`; no message names a chain, an index, a path or code, so a caller cannot choose the worker's entry, runtime or chain index. Worker → main: never a seed, RNG, `RoundKeys`, `RoundDerivation`, authority, runtime, function or path (validators refuse every extra key, getters, non-plain prototypes and typed-array subclasses). A prepared round crosses as its canonical RoundScript bytes (a copy, transferred, so the worker's sent buffer is detached) and its internal digest. **Both are outcome-derived and SECRET until the reveal.**

**Secret residency (both sides; no new invariant is weakened).**

- _Worker:_ the private vault holds the chain's seeds, from which every outcome of the chain can be recomputed; that is its purpose. Its own `RoundScript` object of a prepared round becomes unreachable after the post but is not zeroed (garbage-collected, like any P8-4a script). Seeds, keys and derivations are disposed as in P8-4a. All of it dies with the thread.
- _Main thread:_ the controller re-parses the bytes with `parseRoundScript` and the reported digest (full validation; never skipped), zeroes the transferred buffer afterwards and hands the caller a redacted `RoundScript` (`toJSON`, `String` and `inspect` show no content or digest). The digest also exists as an immutable string in the validated message until garbage collection; strings cannot be zeroed. No derivation, `RoundKeys` or seed copy is created on the main thread by preparation (the crypto provider's own public-vector self-test at `start` is the only one, tested).
- Nothing in `src/prep/` logs, writes files, opens a network connection or reaches the HTTP routes, the WebSocket gateway or the audit sink of the main thread; errors are `PrepWorkerError` with a fixed code and a kebab-case reason (never data). The worker's audit records stay in its own sink (P8-4a fixed codes) and are discarded with it.

**Failures (fail closed; not a production policy).** A worker-reported failure carries its fixed code and `indexState`, read from the vault's reservation frontier before and after: `untouched` (nothing reserved), `consumed` (one index reserved; the P8-4a offline disposition classifies it `aborted`) or `unknown`. Anything but `untouched` halts the worker and the controller: nothing later is reserved. (If the frontier cannot be read _before_ a request, the worker halts and reports `chain-unavailable` / `untouched`; the controller learns of the halt from the next refusal, `worker-halted`, which reserves nothing — a low-severity state-reporting gap, recorded for P8-4b-1.) A worker crash, an unexpected exit, a contract violation (including a skipped index or an altered digest) or `terminate()` rejects **every** pending request as INDETERMINATE and ends the controller; it never restarts a worker and never retries. `start` has no timeout (the controller has no clock by design): a worker that hangs during start leaves `start` pending.

**`MemoryChainStore` is not durable.** The worker's store is in memory only: a crash, an exit or `terminate()` loses the chain's seeds, reservations and dispositions, and the outcome and disposition of every pending request become UNKNOWN. **Crash recovery, durable index uniqueness across restarts and a production abort / void policy are NOT provided and NOT claimed** (P8-7; D10 / OD-11 open). Uniqueness of indices holds within one live worker only (the vault's reservation frontier; the controller additionally requires exactly the previous index + 1).

**Selective abort.** The controller's public API (`start`, `prepare`, `close`, `terminate`, `state`, `inFlight`) has no operation that names, voids, re-draws or retries an index, and nothing the main thread sends depends on an outcome; a request id or salt cannot be replayed onto a used index. What it cannot prevent in P8-4b-0: a caller that has seen a prepared outcome can leave it unused (its index stays `prepared` in the worker's store) or end the whole in-memory chain (`terminate` / `close`) and start a new random chain. In this offline prototype no chain is publicly committed, no round is played and nothing is durable, so neither is observable afterwards. Before any live use, a strictly in-order consumer (P8-4b scheduler), public chain commitment before preparation, a durable store (P8-7) and the D10 / OD-11 policy must make every prepared index accountable.

**Not a security boundary.** A worker thread isolates the main event loop from round preparation (performance). It shares the process: compromised code in the same process is not contained.

**Integrity — protected (owner-approved expansion, 2026-11-24).** `server/src/prep` is a protected directory (`PROTECTED_DIRECTORIES` and `PROTECTED_PATH` of `integrity.ts` and `scripts/engine-integrity.mjs`, kept equal by a test). The trusted manifest now lists **32 files**: the 29 files of §15 unchanged except `server/src/round/integrity.js` (its protected-set rules), plus `server/src/prep/controller.js`, `prep-worker.js` and `protocol.js`; the engine bundle is unchanged (`2d1e5bf8…`). The candidate was generated from a clean build, its paths, sizes and SHA-256 values checked independently against two builds, and its difference to the previous manifest is exactly those four entries. Both sides check: the controller requires the manifest to name the worker files, verifies every protected file and checks its own loaded module closure before it creates a worker; the worker loads and verifies the runtime as before, then checks its own loaded closure. A changed byte, a missing or extra file in `src/prep/`, a stale 29-file manifest or an entry that loads a module outside the protected set is refused, and `npm run build` fails and removes the bundle. **A-1 and A-2 apply unchanged** (the in-process checks verify themselves; an attacker who rewrites the build and the manifest, or code in the same process, defeats them).

## 17. Hardened and bounded RoundScript verification (P8-4b-1, offline development only)

**Status: delivered and independently audited 2026-11-24 under the owner's P8-4b-1 authorization. ACCEPTED FOR OFFLINE LOCAL DEVELOPMENT ONLY (owner, 2026-11-24) after the audit's corrections and a root run on AC power (docs/15); committed locally, not pushed. OFFLINE DEVELOPMENT AND TESTING ONLY — no Global Scheduler, no live scheduling, no network integration, no settlement. PLAY MONEY ONLY.**

**Untrusted bytes (`src/round/canonical.ts`).** `snapshotBytes(bytes, maxBytes)` accepts a `Uint8Array` (Buffer included), reads its length with the intrinsic `%TypedArray%` accessor and refuses anything above the cap **before** it copies or allocates; it then takes ONE private copy with the intrinsic `%TypedArray%.prototype.set`. Nothing reads the input again, and neither the input's own nor a subclass `Symbol.iterator`, getter or prototype member is consulted. Everything later — `prescanCanonical`, strict UTF-8 decoding, `JSON.parse`, the canonical check (`CanonicalCheck`, an explicit-stack comparison that accepts exactly the texts `canonicalJson(JSON.parse(text)) === text` accepts) and the digest — reads only that copy. A shared buffer written by another thread therefore cannot make the validated content and the kept bytes differ (P8-4b-0 race, oracle 208 / 400 divergent → 0), and an input whose iterator yields other bytes cannot either (P8-4b-0 kept `Uint8Array.from(bytes)`).

**Byte cap and prescan (`src/round/round-script.ts`).** `MAX_ROUND_SCRIPT_BYTES = 196,608` (protocol `MAX_SCRIPT_BYTES` states the same literal so that `protocol.ts` stays pure; a test keeps them equal). It is proved: a skeleton document with every field at its longest possible text and every array at its longest length bounds every acceptable script at 148,738 bytes (the longest constructed valid script is 145,584 bytes). `ROUND_SCRIPT_SHAPE_LIMITS` bound nesting, array and object sizes and the container count; the prescan only refuses inputs provably outside what the validators accept. A 4 MiB hostile message is refused in ≈ 0.025 ms (P8-4b-0: ≈ 4.1 s or an out-of-memory crash).

**`RoundScriptVerification`.** `begin(provider, bytes, expectedDigest?)` copies, prescans and parses; `step(budget = DEFAULT_VERIFICATION_BUDGET /* 512 */)` performs at most `budget` operations (canonical check, document, dive samples, creatures, tail, freeze, digest) and returns `null` until the last one, which returns the `RoundScript`. Nothing is exposed before the end; `cancel()` or a failed step ends it and zeroes the private copy; a completed one hands the copy to the script. `state` is `running`, `verified`, `failed` or `cancelled`; the object shows its state only. `parseRoundScript` is the same verification run to completion, with the same errors (`script-invalid`, `script-digest-mismatch`, no detail).

**Controller (`src/prep/`).** Every worker event — message, error, exit — is queued and handled one at a time in arrival order. A `prepared` result is verified in 512-operation slices with one event-loop turn between them, and the received buffer is zeroed as soon as the private copy exists; no later event is handled before it finishes. `terminate()` or a terminal failure during a verification cancels it and rejects the request as INDETERMINATE (never retried). The worker reports a frontier read failure before a request as `worker-halted` / `chain-unavailable`, and the controller halts on `worker-halted` (closes the P8-4b-0 gap in §16). `start()` fails with `start-failed` / `startup-timeout` after `PREP_START_TIMEOUT_MS` (30 s, fixed). At most chainLength + `REQUEST_ID_SLACK` (64) request ids are retained, none evicted; then every request is refused with `request-ids-exhausted` before sending. The protocol accepts `prepared.bytes` only as a plain `Uint8Array` that is the whole of its own non-shared, fixed-length `ArrayBuffer`, 2 … 196,608 bytes, checked with intrinsic accessors before any byte is read.

**Delivery is not durability.** A `prepared` result that arrived before a worker `error` / `exit` is still verified and resolved; the failure is processed afterwards in the same drain, before the caller's continuation runs. A fulfilled `prepare()` therefore means _validated content with the expected index sequence_, **not** a durable disposition: the in-memory chain dies with the worker (`MemoryChainStore`, P8-7; D10 / OD-11). While such a loss is queued, `state` still reads `ready` but `prepare()` already refuses (`not-ready` / `worker-lost`). The future scheduler must treat both accordingly.

## 18. Offline deterministic Global Round Scheduler (P8-4b-2, offline development only)

**Status.** Implemented 2026-11-25 under owner decisions SD-1 … SD-10. Independent acceptance audit (2026-11-25): ACCEPT ONLY AFTER SPECIFIC CORRECTIONS. **IMPLEMENTED, SECURITY CORRECTIONS APPLIED (H-1, M-1, L-1, L-2; 2026-11-25), BUT NOT YET FINALLY ACCEPTED OR COMMITTED** — uncommitted, awaiting owner approval. Not production-ready. PLAY MONEY ONLY. Not connected to the startup, HTTP routes or WebSocket gateway (source and run-time boundary tests); it creates no timer or loop, refuses a production `NODE_ENV`, and has no reveal protocol (P8-4b-3, SD-7), betting, cashout, wallet, settlement or durable storage.

**Modules (`src/scheduler/`).** `clock.ts` (injected monotonic bigint clock; `SimulatedClock`; an unwired `process.hrtime` adapter; tick k's instant is `epoch + floor(k · 10⁹ / 60)` ns, never accumulated), `timeline.ts` (the engine's durations: betting 300, impact → bonus 84, crash banner 144, global pick window 360, chest result 132 ticks, zero gap; admission deadline 240), `events.ts` (fixed-code errors; ordered public events; bounded, hash-chained event log), `sealed.ts` (a prepared script is sealed on receipt: only public metadata is readable; opened exactly once), `disclosure.ts` (the only reader of secret content: tick-gated, monotonic, next-tick-only), `core.ts` (pure deterministic tick-domain state machine), `source.ts` (the approved adapter over the unchanged `PrepWorkerController`), `scheduler.ts` (`GlobalRoundScheduler`, the driver; one per process).

**Timeline and admission.** One active round; round n + 1 opens on round n's end tick. Round n + 1 is requested at round n's opening tick S and must be held (delivered and verified) before tick S + 240, inside round n's fixed betting window — never at round n's own (secret) end. Otherwise the scheduler halts after round n: no delay, retry, skip or substitution. Active + held / admitted + requested scripts ≤ 2. Every tick is processed in order, so late or irregular polling never changes an event's tick or an outcome; but a stall of more than 240 ticks after an opening tick halts (fail closed), and a single late poll that crosses an opening tick and its admission tick in one catch-up halts in the same way (the request is only sent at the opening tick). Round ids: SHA-256 over `"AQUADIVE|scheduler|round-id|v1" ‖ 0x00 ‖ chainId ‖ u64be(index) ‖ u64be(round)` (fixed-length fields, injective; collisions only through SHA-256).

**Disclosure.** Each event is public at its own tick: `round.betting` (round id), `round.dive`, `round.boost` (goldfish consumption, no creature data: OD-5), `round.crashed` (crash point), `round.impact` (jackpot), `round.bonus` (no chest values), `round.chests` (the three values when the pick window closes), `round.ended`. A floor round never discloses its crash point. Snapshots show the current tick's multiplier only. Seals, disclosure cursors, the core, the driver and the source print public state only.

**Failures (not a D10 / OD-11 policy).** Deadline miss, chain exhaustion (SD-10), preparation failure, worker loss: the active round finishes, then halt; after a worker loss its reveal is `unavailable` (SD-6). Contract violation, owner stop, an invalid clock reading (`clock-failed`) or an unexpected internal error (`internal-error`, the source is terminated): immediate halt, the active round is interrupted (not a settlement outcome, never "completed"). Nothing is restarted or retried; a source serves one scheduler and only that scheduler can request.

**Security corrections (2026-11-25, after the acceptance audit).**

- **H-1 source substitution (critical, fixed).** `create()` checked `options.source` and then re-read it, so a getter or Proxy could pass the approved source to the check and a forged source (caller-built seals, chosen outcomes) to the scheduler; reproduced in compiled CommonJS (forged chain, crash points 99.99× then 1.00×). Now the options are read exactly once: Proxies and accessor properties are refused, each key's value comes from one descriptor read, the clock's `nowNs` is captured once, and only those verified references are used afterwards. Eight hostile variants are refused in compiled CommonJS; a refusal does not use up the process's scheduler, and the legitimate source and its one-time claim are unchanged.
- **M-1 seal opening capability (fixed).** The static `Symbol("SealedRound.open")` (found by `Object.getOwnPropertySymbols`) and the exported `openSealedRound` are gone. The opener is a closure from the class's static block in a module-private binding; `claimSealedRoundOpener()` hands it out once per module instance, and `disclosure.ts` claims it as it loads, so every other claim is refused (`sealed-misuse: opener-claimed`). A fresh module instance cannot open this instance's seals (private brand). This protects against ordinary callers only, NOT against arbitrary privileged same-process code (loader hooks, a patched build, the inspector; A-1).
- **L-1 clock safety (fixed).** Every reading is checked before use: a throw, a non-bigint, a negative value, a backwards reading or a tick overflow halts at once with `clock-failed` at the last processed tick, nothing of that reading is processed, and `start` / `poll` throw a fixed-code error. Previously a backwards or negative reading was silently ignored (frozen timeline) and a throwing clock leaked its own message. A stalled (equal) reading is valid: no ticks pass.
- **L-2 asynchronous failures (fixed).** Every step and every source result runs inside one fail-closed guard: queued seals are discarded unopened, the interrupted step's pending effects are dropped (no request after a halt), nothing is retried, and results that settle after the halt are discarded. The source additionally contains a throwing listener (script discarded, worker stopped). Previously a clock failure inside a delivery produced an unhandled rejection and dropped the seal without discarding it.

**Integrity (owner-approved expansion).** `server/src/scheduler` is a protected directory (`integrity.ts`, `engine-integrity.mjs`). Trusted manifest 32 → 40 files: + the eight `server/src/scheduler/*.js`, changed `server/src/round/integrity.js`; the other 31 entries and the bundle (`2d1e5bf8…`) unchanged; manifest `3c4fc346…`.
